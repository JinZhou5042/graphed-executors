# m69b frozen suite — histserv servers as executor services, and the H->gg diagnostics

This suite freezes the executors' side of m69b in `lanes/htcondor/plan-services.md`: the m69b
executors unit's "Placement", "Schedulability", "Ordering" and "Diagnostics" paragraphs and their frozen
tables.
graphed-histogram's `graphed_histogram.histserv` (`Context`, `Histogram`, `Receipt`) and `gh.plan`'s
served plans are the code these tests drive; it is reached only through `m69b_harness.histserv_api()`
inside test bodies, so the directory collects before that module exists.

## Running

- `pytest tests/frozen/m69b` collects anywhere. `tests/frozen/m68a` (for `services_harness`) and
  `tests/frozen/m69a` (for `hgg_harness`) are on pytest's `pythonpath`.
- The `test_histserv_*` files need `histserv` wherever the GIL is enabled (a missing one fails). A
  free-threaded interpreter skips them, since grpcio has no cp314t wheel.
- `test_histserv_cluster.py`'s live tests need the `htcondor2` bindings and a pool (the
  `test-htcondor` job). Without the bindings they skip; with bindings and no schedd they fail. Its
  narrowing refusal needs neither.
- `test_service_order.py`'s recorder rows run on every OS with the base install (no bindings, no
  histserv). Its pool rows are gated as `test_histserv_cluster.py`'s, and the `test-htcondor` job runs them
  only once its file list names this file. The Ctrl-C row is POSIX only.
- The `test_hgg_*` files skip without coffea, higgs_dna or histserv. With `GRAPHED_HGG_REQUIRED=1`
  (the `test-hgg` job) a missing one fails instead.

## Readings of the plan these tests rely on

- The diagnostics are the seven names the plan lists with their binnings (the prose once said "six";
  the named set governs). Each fills its column of the part (`mass`, `pt`, `lead_pt`, `sublead_pt`,
  `lead_eta`, `sublead_eta`, `n_jets`) with `weight`.
- `ctx.servers()` rows are `(name, memory_mb, predicted_bytes, n_histograms)`, and `memory_mb` is in
  MiB. A receipt's `endpoint` is the endpoint its server was bound at.
- The `service_hosts` narrowing refusal is a `ValueError`, the codebase's refusal type for invalid
  arguments (`submit_driverless`, `CondorPilots`).
- A driver-check `ServiceUnavailable` names the numbers as plain integers. The host's memory is read
  as the plan states it, floored to the MiB.
- A condor refusal's text is read from the exception and its `legs` together, since the engine may
  carry `host_service`'s refusal in a leg.
- The idle log is a record on a `graphed_executors` logger at INFO whose message names the waiting job's
  key (its `JobBatchName` after `graphed-service-`) and `JobStatus=1`; the busy-pool test captures it.
- A driver job's refusal is read from `result.pkl`'s `(False, error)`, the error and its `legs` together,
  with the run's `tmp_path` cut out, so the slot memory it names cannot come from a path.
- A later plan holds its runner's queued pilots once, before its first service submit, and releases them
  once, at its next need of a worker, after its last announce (the dispatch decision for a plan with several
  services). The Hold's constraint names the pilots' cluster and `JobStatus == 1` and its `act` passes a
  `reason`; the Release's constraint names the pilots' cluster and that reason's text, so a hold the user
  placed is not released.
- `CondorPilots.prepare` writes the pilots' `graphed-secret` when the backend is built, before any pilot is
  submitted.
- A refusal names the pilots' cluster as the word `cluster` followed, within 16 non-digit characters, by its
  id, in the exception and its `legs` together with the run's `tmp_path` cut out.
- "Within `POLL_S` + 2 s the plan raises" is read from the raise in the `with` block to the block's exit,
  which waits for `close()`.
